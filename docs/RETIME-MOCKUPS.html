Retime selected strokes

Feasibility review and mockups · 2026-10-22 · Editor feature, not built

The ask: select strokes in the Editor, set the date and time of the earliest selected stroke, and shift every other selected stroke by the same amount so their relative timing is unchanged.

Everything that reads time downstream (Timeline, Dates, capture-date index, task dates, the reader's "written on") already derives it from stroke startTime at scan time, so once the PageDoc is right those views follow after refreshAfterSave(). _timeline.json re-reads a page whenever its mtime changes, so it needs nothing.

The one hard part: the id is the timestamp

Every stored stroke's id is s{startTime} (strokeToStored(), generateStrokeId()), and the save is append-only, deduped by id. If the Editor just changed startTime and saved:

  1. The retimed stroke has a new id that isn't on disk, so the save appends it.
  2. The old id is still on disk and isn't in the explicit deletion set, so the save keeps it.
  3. Result: every retimed stroke exists twice, once at each time. Nothing warns.

That's exactly the volume-move bug the movedFrom marker already prevents. The fix has the same shape:

// in-memory only, like movedFrom / pointsEdited (strokeToStored never copies it)
stroke.retimedFrom = { id: 's1760447525107' }   // the id that is on disk now, kept from the FIRST retime

getDeletedStrokeIdsForPage()     → delete   retimedFrom.id ?? generateStrokeId(stroke)
getMovedAwayStrokeIdsForPage()   → move off retimedFrom.id ?? generateStrokeId(stroke)
new getRetimedAwayStrokeIdsForPage() → unioned into deletedStrokeIds by the save, like moves
Two existing paths would quietly break without this. Deleting a retimed stroke before saving, and moving a retimed stroke to another volume, both compute the disk id from the current startTime. After a retime that id isn't on disk, so the deletion or move-away finds nothing and the old copy survives. Both must read retimedFrom.id first.

Collisions

A uniform shift keeps the selected strokes distinct from each other, but a shifted stroke can land on the exact millisecond of a stroke that is not selected on the same page. The dedupe would then silently drop it. onDiskStrokeIds already holds every stored id for each canvas page, so the dialog can check before applying, plus unsaved canvas strokes. Collisions are rare (millisecond resolution); the proposal is to refuse with a message and offer "+1 ms" rather than silently nudging.

Times are local (same day rule as dayKeyLocal). Seconds are shown because a session's strokes can be seconds apart; milliseconds are kept from the original. Try setting a time in the future, or exactly 2026-10-14 13:05:00, to see the warning and the collision states.

States the dialog handles

  • No change: Apply disabled.
  • Into the future: warning, still allowed.
  • Collision: a shifted stroke would share an id with an unselected stroke on its page → Apply disabled, "+1 ms" offered.
  • Before 2000 / NaN: refused (guards a typo like year 0202).
  • Pasted (unplaced) strokes are excluded: they already have synthetic times and aren't saved until placed.

After Apply

  • Strokes keep their selection, so a second retime is easy; retimedFrom keeps the first original id.
  • Activity log: "Retimed 38 strokes by +11 d 4 h 53 min".
  • Undo before save: Reset in the dialog (shift back by the stored Δ), or Revert.
  • The Editor's Dates tab and day colours follow immediately; the Timeline and Library follow after Save.

Build plan

  1. Pure helper lib/retime.js: shiftStroke(stroke, deltaMs), retimeDelta(strokes, newStartMs), findRetimeCollisions(shifted, onDiskIds, canvasIds), daysAfterShift() for the preview. Unit tests at the boundaries: null point timestamps, short tuples, Δ = 0, DST transitions, a page with mixed retimed and fresh strokes.
  2. Store action retimeStrokes(indices, deltaMs) in stores/strokes.js: stamps retimedFrom once, calls markUnsavedChanges(); clearRetimedMarkers(book, page) after save.
  3. Id plumbing in pending-changes.js: deletion and move-away read retimedFrom.id; new getRetimedAwayStrokeIdsForPage(); a retimes bucket in computePendingChangesMap(), and the same in computePageChangesFolder(). Save handler unions the ids into deletedStrokeIds.
  4. Dialog components/canvas/RetimeDialog.svelte (new file; StrokeCanvas is already over the size guideline, so it only gets the button). aria-modal, Escape handled with preventDefault().
  5. Save dialog row + CHANGELOG / ARCHITECTURE / TESTING updates.

Risks and open questions

  • Re-importing pen memory brings the old strokes back. Offline import dedupes by id. If the pen still holds those strokes and you import again, they come in at the old times with their old ids, which are no longer on disk, so they're added as duplicates. Options: (a) a small _retimed.json sidecar of old → new ids per page that import consults, or (b) just warn in the dialog and recommend clearing pen memory after import. Recommendation: (a), since import is exactly when a bad pen clock shows up. Your call.
  • Already exported to LogSeq. mergeGraphStrokes() lets the published copy win by id, so re-exporting a retimed page would add the new-id copy beside the old one in the graph. Simplest: refuse retime on strokes that have been exported, or document it. Worth checking whether you still use Export to graph.
  • Pen clock offsets are usually whole-batch. If the typical case is "the pen's clock was wrong for a whole import", a Shift by… field (±days/hours) might be faster than picking an absolute time. The mockup's nudges cover most of that; a second mode is cheap to add later.
  • Partial page loads. Only loaded strokes can be selected, and the collision check uses the full on-disk id list, so this is safe; it just means retiming a whole page wants the whole page loaded.
  • Tasks and tags. A task's date is its page's capture days, so retiming moves where tasks group in "date written". Tags are keyed by page, not time, so they're unaffected.
