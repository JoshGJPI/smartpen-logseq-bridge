1Tag a page in the reader

When a page is open in the Library reader, a narrow side strip shows its tags. It sits beside the page, so the handwriting keeps its space. Type, pick or press Enter, and a tag saves immediately. Tags don't count as an unsaved edit: they're written straight away, like page rotation.

2Suggested project numbers new behaviour

When the open page's transcript contains ####-### or P####-###, the strip offers it as a dashed chip, with the transcript line it came from underneath. ✓ adds it as a real tag, ✕ dismisses it for this page (and it stays dismissed). Nothing is tagged without a click. A page with no transcript shows no suggestions.

3Tags on the page grid, and bulk tagging

Thumbnails in a notebook's page grid show their tags under the page number (first two, then "+N"). A small amber dot marks a page that has an unreviewed project-number suggestion. Select turns on tick-circles; with pages ticked, a bar appears to add or remove a tag from all of them.

4Group by Notebook | Tag

The Library home keeps its existing sort chips and gains a Group by toggle. In Tag mode each card is a tag. A card shows the page count, how many notebooks it spans, and a thumbnail strip of its most recent pages. Opening a card shows that tag's pages across all notebooks (mockup 5). The last choice is remembered.

Try it: switch Group by to Tag. Sort chips follow the grouping: in Tag mode they read Most pages · Name · Recently tagged/written. Project-number tags group together under a Projects heading so keywords don't bury them. An Untagged card (dashed) keeps un-tagged pages reachable.

5Opening a tag, and filtering any grid

A tag's page grid is the same grid as a notebook's, with two differences: every thumbnail's label also names its notebook, and a filter row sits above. The same filter row appears in a single notebook's grid, so "filter" works both ways: group by tag, or stay in a notebook and narrow it.

AnyAll

Try it: click tag chips to add them to the filter, switch Any / All. Any = pages with at least one chosen tag, All = pages with every chosen tag. Only tags that exist on pages in the current grid are offered, each with its count, so you can't filter to an empty result by accident.

6Suggestion review queue new behaviour

Going page by page to accept suggestions would be slow for a back catalogue. A small Suggestions entry on the Library home (with a count badge) opens a queue of every transcribed page that has an unreviewed project-number suggestion, grouped by number so the same job across pages is one decision.

7Tag manager

Settings gets a Tags section, deliberately plain: a table of every tag with its page count, and rename / merge / delete. Renaming to a name that already exists is a merge (with a confirm). Deleting a tag only removes the label from pages; it never touches a page.

Try it: Rename and Merge show the confirm text they'd use. Merge asks which tag survives. Counts come from the sidecar, so they're instant and never read a page.

Spec notes behind the mockups

Storage: pages/_tags.json

Same family as _orientation.json: read and written through main-process IPC, atomic write, serialized, a missing or corrupt file means "no tags". Page keys are "<bookKey>/<pageId>", so suffixed pages (P151b) and volumes (388v2) work as everywhere else.

{
  "version": 1,
  "pages":     { "3017/42": ["beam", "P2026-141"], "388v2/7": ["2327-018"] },
  "dismissed": { "3017/42": ["2327-018"] }
}
  • Tags are normalized on write: trimmed, internal whitespace collapsed to -, lowercase, except project numbers, which are stored as P####-### / ####-###. Sorted, de-duplicated, max length (proposal: 40 chars).
  • Display-only metadata: no PageDoc is touched, no unsaved-changes dot, no refreshAfterSave(). A pageTags store feeds views, as pageOrientations does.
  • Volume reassignment is a move, so it must carry the page's tag and dismissed entries to the new key (small hook in the move path, with a test).
  • Indexes (tag → pages, tag counts) are derived once per change in a pure lib/tags.js, never per render.

Suggestion rules

  • Pattern, roughly (?<![\dA-Za-z])P?\s?\d{4}[-–—]\d{3}(?!\d) over each transcript line's text, then normalized as in the table in mockup 2.
  • Pattern only, not validated. The app can't know if a number is a real project (that needs LogSeq or BQE). A wrong number is one ✕. If you later want validation or a project title next to the chip, it can be a lookup layered on top and doesn't change the storage.
  • Computed from the page's stored transcript when needed (reader open, queue open). Nothing about suggestions is stored except dismissals. Pages are read lazily; the queue reads transcribed pages in the background with a progress count, not in the metadata scan (scans stay metadata-only).
  • Not suggested if already a tag on the page or dismissed for that page.

Performance and safety checks

  • Tag counts and grouping read only the sidecar plus the existing scan records, so the home and tag cards cost nothing extra at any page count.
  • Thumbnail tags come from the store, not from reading pages. The thumbnail loading rules (on-screen only, off the page cache) are unchanged.
  • Failure modes: data folder missing → tag UI disabled with the same message as other folder features; write fails → chip rolls back with an Activity Log entry; two quick edits can't overwrite each other (serialized, per-page merge in main).
